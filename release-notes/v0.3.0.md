# oh-my-deepseek v0.3.0

## 本版新增：对话完成的系统通知

当一轮回复结束、而你没有在看窗口时，客户端会弹一条系统通知：标题是这段对话的标题（harness 还没生成标题时用 workspace 目录名），点一下回到窗口。你正看着窗口时不会打扰你。开关在「高级」里，默认开启。

实现上**不往 harness 里塞任何东西**——容器不参与 turn 生命周期，也不注入 harness 的 UI（那会被 harness 的版本升级搞坏）。改为只读 harness 自己写的、带版本的会话日志 `session.v3.jsonl.zstd`：

- 日志是**一串各自独立的 zstd 帧**，所以容器只解析帧结构定位边界、只解压没读过的帧。Node 自带的 `zstdDecompressSync` 只解第一帧，因此帧扫描是必需的而不是优化
- 判定信号是 `turn/end`，从中取轮次与结束原因
- **子代理会话被排除**：头帧的 `delegationDepth` 非 0 即被委派，它们自己的 turn 结束不代表你的对话结束——不排除就会在你还在等的时候提示"完成了"
- 首次看到的日志只作为历史记录、不产生通知，所以打开客户端不会被历史对话刷屏

> 共用数据目录时，命令行 dsh 的对话也会被一并监听并提醒（日志在同一份 home 下）。想只提醒客户端自己的对话，就用独立数据目录。

### 顺带修掉的一个平台坑：macOS 上未签名的包根本弹不出通知

Electron 42 起，macOS 通知从废弃的 `NSUserNotification` 改为 `UNNotification`，后者**拒绝显示任何来自未签名应用的通知**，而且失败是**静默**的——`Notification.isSupported()` 照样返回 `true`、`show()` 不报错，只有 `failed` 事件里才有原因。

更隐蔽的是，Electron 发行版**自带**的签名也不满足要求：它是链接器打的 `flags=0x20002(adhoc,linker-signed)`、identifier 为 `Electron`，恰好属于被拒绝的那一类。

所以本版起，打包流程在没有真实证书时会用**应用自己的 identifier 做一次 ad-hoc 签名**（`flags=0x2(adhoc)`、`Info.plist` 绑定、资源封印、`codesign --verify --strict` 通过）。这不是美化：不做这一步，通知在这台机器上永远不会出现，设置里也找不到这个应用。容器同时会监听 `failed` 事件并把平台给的原因写进日志。

> 首次可能弹一次钥匙串授权（Electron Safe Storage）。ad-hoc 签名没有稳定身份，重新构建后 macOS 可能再问一次；配好 Developer ID 之后就不会了。

## 历史版本（0.2.0）：客户端自身的更新

控制台多了一张**「客户端」**卡片，管的是**这个客户端本身**的版本，和下方的 Harness 版本互不相干：

- 启动时会去项目的 GitHub Releases 查一次最新版本（可在「高级」里关掉），也可以手动「检查客户端更新」
- 有新版会显示可更新到的版本、下载按钮，以及通往发布说明的链接
- 下载先写 `.part`，**传输完成且字节数与发布页声明一致**才改名落地，半截文件永远不会被拿去安装

不同平台能做的事不一样，界面会照实说明：

| 平台 | 下载后 | 原因 |
| --- | --- | --- |
| **Windows** | 直接运行安装包并退出客户端，安装程序替换自身 | NSIS 不需要代码签名即可完成替换 |
| **macOS** | 打开下载好的磁盘映像，你把 App 拖进「应用程序」 | **未签名的构建无法静默自更新**：Squirrel.Mac 要求运行中的 App 已签名、且新版本签名匹配，而本项目的构建刻意不签名 |

所以 macOS 上是"下载 + 引导替换"，不是一键静默升级。检查、选包、下载这三段是跨平台共用的——**以后配好 Apple Developer ID 签名与公证，只需替换 `installRelease()` 就能拿到真正的静默自更新**。

## 历史修复（0.1.1）

**客户端外壳现在跟随系统的浅色/深色设置。** 之前控制台窗口和窗口背景是硬编码深色，所以在浅色桌面上会出现"浅色菜单栏下压着一块深色面板"。harness UI 本身在系统换色时是会重绘的（它的主题偏好默认就是跟随系统），不一致的是容器自己的外壳。

现在 `console.css` 里的每个颜色都是 token，一条 `prefers-color-scheme` 查询重绘整个窗口；窗口背景由 `appearance.ts` 提供，并在 `nativeTheme` 报告变化时重新应用——所以已经开着的窗口也会跟着切换，而不是保留旧颜色。

自动化验证会断言控制台的实际渲染背景与系统外观一致（两个方向都查），并用 `--smoke-theme` 强制另一种外观，确保这台机器当前没用到的配色也被验证过。

> 另外提一句上个版本就该有、但值得写下来的修复：**GUI 启动的 PATH**。客户端由 Finder 启动时继承的是 launchd 的最小 PATH，harness 因此看不见任何 Homebrew 安装的工具（装了 `ffmpeg` 却报缺失）。现在会注入终端风格的 PATH。

DeepSeek Harness（`dsh`）的桌面客户端容器：**打开就能用，不需要命令行、不需要 `pnpm dsh web`；关闭客户端时后台进程随之关闭。**

> ⚠️ **非官方项目**：由社区独立开发，与 DeepSeek 官方**没有隶属、合作或背书关系**。官方项目见 [deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)。

## macOS (Apple Silicon)

### 安装

这个包**没有签名、没有公证**，首次打开会被 macOS 拦截：

1. 把 `Oh my deepseek!.app` 拖进「应用程序」
2. **右键点图标 → 打开** → 弹窗里再点「打开」
3. 之后就能正常双击启动

（或：`系统设置 → 隐私与安全性` → 拉到底点「仍要打开」）

核对 SHA-256：

```sh
shasum -a 256 oh-my-deepseek-0.3.0-mac-arm64.dmg
```

### 开箱即用

首次启动**不需要联网**：包内已带 dsh `0.1.5-rc.1` 的完整生产依赖树（519 个包）与内置 npm（用于在客户端内安装/切换 dsh 版本）。启动后自动准备后端并打开 Harness 界面。

### 限制

- 仅 arm64；Intel Mac 需自行执行 `npm run package:mac:x64`
- 未签名、未公证
- 不做外壳自更新；客户端内的「更新」指的是更新 dsh 版本

## Windows (x64)

### ⚠️ 请先读这一节

**这个 Windows 包没有在 Windows 上实测过。** 它是在 macOS 上交叉打包出来的：产物生成正常、图标与资源校验都通过，但**启动、对话、退出行为都没有在真实 Windows 上验证**。请当作预览版使用。

跑出问题欢迎开 issue，附上 `%APPDATA%\Oh My DeepSeek\logs\container.log`。

### 安装

安装包**没有代码签名**，SmartScreen 会拦截：

1. 运行 `oh-my-deepseek-0.3.0-win-x64.exe`
2. 若出现「Windows 已保护你的电脑」→「更多信息」→「仍要运行」

核对 SHA-256（PowerShell）：

```powershell
Get-FileHash .\oh-my-deepseek-0.3.0-win-x64.exe -Algorithm SHA256
```

### 首次启动需要联网

包里没有内置 dsh，首次启动会用内置 npm 自动下载安装（约 280 MB、数百个包，通常 30 秒左右，取决于网络）。控制台会显示进度，之后即可离线使用。

### 限制

- **未在 Windows 上验证**（见上）
- 未签名，SmartScreen 会提示；**首次启动需要联网**
- **长路径风险**：dsh 依赖树较深，装在很深的目录下可能触碰 260 字符上限。建议用默认安装位置，或启用 Windows 长路径支持
- 关闭最后一个窗口即退出

## 两个平台共同的行为

### 客户端里能做什么

控制台（macOS：菜单栏 **Harness → 控制台** / `Cmd+Shift+C`；Windows：`Ctrl+Shift+C`）：

- 查看后端状态、端口、进程号与实时日志
- **Harness 版本**：列出 npm 上全部已发布版本，一键安装、切换、删除；有新版会提示
- **高级**：在「与命令行共用数据目录」和「使用独立数据目录」之间切换、开关自动启动、打开日志与数据目录

默认与命令行的 `dsh` 共用同一个数据目录（macOS `~/.dsh`，Windows `%USERPROFILE%\.dsh`），所以已有的凭据、会话、技能可以直接用。

### 同一个会话同一时刻只能在一个地方打开

dsh 对每个会话持有内核写租约（POSIX 是 `flock`，Windows 是内核信号量）。如果在命令行里开着某个会话，又去客户端里点开它，会看到：

```
SessionAlreadyOwnedError: session "…" is already owned by an active write handle
```

这**不是 bug，也不是数据损坏**：租约由内核管理，持有进程一退出就自动释放（不存在残留死锁），而且**故意不设超时抢占**——否则卡住的写者恢复追加会撕裂会话日志。想彻底不再遇到，就用控制台里的「使用独立数据目录」（切换时会自动复制凭据，不需要重新登录）。

## 已验证的内容

macOS 包在真机（macOS 26.6.2 / Apple Silicon）跑过完整端到端自检：

- 打包产物真实启动、Harness 页面加载成功、鉴权围栏生效（未鉴权 `401` / 一次性 token `303`）
- 应用内安装并切换到 dsh `0.1.5-rc.2`，页面在新版本上重新加载成功
- 正常退出：后端约 1s 内停止，无残留进程
- **主进程被 `SIGKILL` 强杀**：supervisor 在 ~0.7s 内回收整个后端进程组，无残留
- 切换独立数据目录：凭据与技能被复制（权限 `0600`）、会话不被复制、可切回
